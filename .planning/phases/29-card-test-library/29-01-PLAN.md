# Phase 29 — Plan 01: Card Test Library

## Goal
Build a scalable visual test library that covers every card in the game — using a factory pattern rather than writing 70+ individual tests. The library is structured in three layers:

1. **Effect-category specs** — one file per tag/effect type, tests a representative card from that category
2. **Data-driven card registry** — a single test-data file listing every card with its expected outcome; a shared test runner loops over them
3. **Chain/combo specs** — explicit tests for known multi-card interactions and synergies

The result: adding a new card = adding one entry to the registry file. Writing a new chain = adding one test to the combo spec.

---

## Why NOT one file per card

70 piecies × ~10 lines each = 700+ lines, all nearly identical. Adding a card means copying boilerplate. A bug in the shared setup gets fixed in one place, not 70. The factory approach is already how the game engine works — card definitions are data, effects are functions. Tests should mirror that.

---

## Layer 1: CardTestSpec format (`card-registry.js`)

Each entry in the registry describes exactly what a test should do and assert:

```js
export const CARD_REGISTRY = [
  {
    cardId: 'piecie_kannetje_melk',
    deckId: 'PHYSICAL_FORCE',         // or a custom deck object
    cardType: 'PIECIE',
    setup: { mpSlot0: 30 },           // testHook overrides before play
    playThen: 'activate',             // 'place-then-activate' | 'play-direct' | 'ability'
    expectedEffect: 'MP_GAIN',        // what the test checks for
    mpDeltaMin: 18,                   // minimum expected MP change (some effects vary)
    mpDeltaMax: 22,                   // maximum expected MP change
    logMatch: /kannetje|melk|\+20/i,  // regex the log must match
    skipReason: null,                 // non-null = skip with this message
  },
  ...
]
```

**Possible `expectedEffect` values:**
| Value | What the runner checks |
|-------|----------------------|
| `MP_GAIN` | mpAfter > mpBefore by mpDelta range |
| `MP_DRAIN` | mpAfter < mpBefore (opponent also drained) |
| `MP_ZERO` | mpAfter === 0 exactly |
| `STATUS_EFFECT` | mpAfter === mpBefore (effect adds status, not MP) |
| `QUEST_BOOST` | mpAfter === mpBefore + questPrepBonus applied (use log match) |
| `DRAW` | hand size increased by expected amount |
| `FIELD_EFFECT` | game state flag is set (via testHooks.getGameState) |
| `PERSIST` | card still on field after activation (persistUntilEndOfTurn) |
| `ATTACK` | opponent Mosje MP decreased |
| `GAMBLE` | mpAfter !== mpBefore (random result, just verify change happened) |

## Layer 2: Card test runner (`card-test-runner.js`)

A shared async function that takes a `CardTestSpec` and executes the standard flow:

```js
export async function runCardTest(page, spec) {
  // 1. Setup: seed deck (custom or starter), navigate, waitForBoard
  // 2. Apply testHook overrides (setMosjeMP, etc.)
  // 3. Record mpBefore (own + opponent)
  // 4. Execute the play action:
  //    - 'place-then-activate': play face-down → endTurnAndWait → activatePiecieOnField
  //    - 'play-direct': playCardFromHand (for snelle piecies, direct play)
  //    - 'ability': click Mosje ability button
  // 5. Dismiss any modals that require choices (target selectors → auto-pick first option)
  // 6. Record mpDuring
  // 7. Check expectedEffect assertions
  // 8. endTurnAndWait (for PERSIST tests: verify card gone)
  // 9. Check log for logMatch
  // 10. Screenshot with card name
}
```

Key insight: for piecies that require target selection (Affoe, Leipe Swap, Stookerino), the runner auto-clicks the first `.target-option` button. This covers the happy-path without custom logic per card.

## Layer 3: Chain tests (`tests/ui/chains/`)

Explicit multi-card tests for interactions that can't be captured by the factory alone:

### `mp-gain-chain.spec.js`
Tests that stacking multiple MP-GAIN piecies compounds correctly:
- Kannetje Melk (+20) → Protein Shake (+15) → verify cumulative MP
- MP Amplifier active → next gain is ×1.5 → verify amplified gain

### `quest-boost-chain.spec.js`
Tests the quest dice modifier pipeline:
- Dubbele Dosis activated (+2 dice) → General Quest → roll with mock dice → verify threshold used modified roll
- Quest Prep (+2) + Sleutelpuntje (+1) stacked → verify +3 bonus on roll

### `attack-chain.spec.js`
Tests ATTACK + PROTECT cancel:
- Play ATTACK piecie (Bikkel Punch or similar) → opponent Mosje MP drops
- Play ATTACK → human plays Not Today! interrupt → verify Mosje survives
- PROTECT snelle (Counter Strikka) vs ATTACK → verify negation + counter MP

### `synergy-combos.spec.js`
Tests Mosje-Mosje and Mosje-Piecie synergies:
- Chris+Youri: piecie from hand goes directly to active state (no face-down turn)
- Verify quest prep bonus resets after quest attempt (not carried to next turn)
- Tony + weapon piecie: verify trait bonus applies correctly

### Task 2 — Build `card-test-runner.js`

The core engine for the card library. Must handle:

1. **Deck setup**: if `spec.deckId` is a string → `seedOfflineSession`; if it's an object → `seedCustomDeck`

   - `place-then-activate`: `playCardFromHand` → `endTurnAndWait` → `activatePiecieOnField`

6. **Log assertion**: `expect(log.join(' ')).toMatch(spec.logMatch)`

### Task 5 — Build `piecie-effects.spec.js`

Loops over all piecie entries in `CARD_REGISTRY` and runs `runCardTest` for each one that isn't skipped:

```js
import { test, expect } from '@playwright/test';
import { CARD_REGISTRY } from './card-registry.js';
import { runCardTest } from './card-test-runner.js';

const piecies = CARD_REGISTRY.filter(c => c.cardType === 'PIECIE' && !c.skipReason);

for (const spec of piecies) {
  test(`piecie: ${spec.cardId} — ${spec.expectedEffect}`, async ({ page }) => {
    await runCardTest(page, spec);
  });
}

// Also runs the skipped entries but marks them explicitly
const skipped = CARD_REGISTRY.filter(c => c.cardType === 'PIECIE' && c.skipReason);
for (const spec of skipped) {
  test.skip(`piecie: ${spec.cardId} — SKIPPED: ${spec.skipReason}`, async ({ page }) => {
    await runCardTest(page, spec);
  });
}
```

**Files:** `tests/ui/cards/piecie-effects.spec.js`

### Task 8 — Build `ability-registry.js` + `mosje-abilities.spec.js`

Abilities are fundamentally different from piecie effects — they're triggered by clicking a Mosje's ability button, not playing from hand. They need their own registry format and a separate `runAbilityTest` runner.

#### 8a — `AbilityTestSpec` format

```js
{
  mosjeId: 'mosje_gandoe_destroyer',
  deckId: 'PHYSICAL_FORCE',         // starter deck or custom deck object
  setup: {
    mpSlot0: 100,                    // own Mosje MP before ability
    opponentMpSlot0: 80,             // opponent Mosje MP before ability (for damage tests)
    handCards: ['piecie_kannetje_melk'],  // cards to inject into hand for cost-abilities
    graveyardCards: ['piecie_kannetje_melk'],  // for discard-retrieval abilities
    youriAbilityUses: 0,             // for Youri cap tests
  },
  expectedEffect: 'OPPONENT_DAMAGE', // see table below
  // Quantitative assertions
  ownMpDeltaMin: -80,               // own Mosje MP change (negative = own cost)
  ownMpDeltaMax: -80,
  opponentMpDeltaMin: -999,         // opponent MP change (negative = took damage)
  opponentMpDeltaMax: -999,         // -999 = eliminated (went to welloe)
  handDeltaMin: 0,                  // own hand size change
  handDeltaMax: 0,
  opponentHandDeltaMin: 0,          // opponent hand size change (negative = discarded)
  opponentHandDeltaMax: 0,
  logMatch: /[Ee]limination|[Ss]trike/,
  skipReason: null,
}
```

#### 8b — `expectedEffect` values for abilities

| Value | What the test asserts |
|-------|----------------------|
| `OWN_MP_GAIN` | ownMpDelta > 0 |
| `OWN_MP_COST_DRAW` | ownMpDelta < 0 AND handDelta > 0 (paid MP, drew cards) |
| `OPPONENT_DAMAGE` | opponentMpDelta < 0 (own Mosje dealt damage to opponent) |
| `OPPONENT_ELIMINATE` | opponent Mosje moved to welloe pile (no longer in activeSlots) |
| `OPPONENT_DISCARD` | opponent hand size decreased |
| `OWN_DISCARD_AS_COST` | own hand size decreased before ability resolves |
| `DRAW_CARD` | handDelta > 0, ownMpDelta = 0 |
| `RETRIEVE_FROM_GRAVEYARD` | hand size increased, graveyard decreased |
| `STATUS_EFFECT` | ownMpDelta = 0 AND a flag is set (immune, questPrepBonus, etc.) via testHooks.getGameState() |
| `DOT_STATUS` | opponent has DRAIN statusEffect in game state |
| `DECK_MANIPULATION` | deck + hand size relationship changed (top-5 scry) |
| `GAMBLE` | ownMpDelta ≠ 0 (positive or negative, random — just verify something changed) |
| `CONDITIONAL_MP` | ownMpDelta depends on setup (comeback, adaptive) — use setup to guarantee condition |
| `TRANSFER_MP` | total MP of own slots unchanged, but distribution between slots changed |
| `PASSIVE` | ability fires automatically — no button click needed, verified via log |
| `ALREADY_COVERED` | skip — ability already tested in mechanics.spec.js |

#### 8d — `runAbilityTest` function

The ability runner is separate from the piecie runner. It:
1. Seeds the deck and navigates to the board
2. Applies `setup` overrides via `testHooks` (MP values, hand manipulation, graveyard seeding)
3. Injects `_pendingTargets` for abilities that need pre-set targets (via `testHooks` or `addInitScript`)
4. Finds the correct Mosje card on the board by `data-card-id`
5. Clicks its `.mosje-ability-btn`
6. Handles any modal that appears (auto-dismiss or auto-pick first option)
7. Reads state after: own Mosje MP, opponent Mosje MP, hand sizes, graveyard sizes
8. Applies assertions per `expectedEffect`
9. Checks `testHooks.getGameState()` for status effects and flags (immuneThisTurn, questPrepBonus, statusEffects array)

```js
// tests/ui/cards/ability-runner.js
export async function runAbilityTest(page, spec) {
  // Setup, navigate, waitForBoard
  // Apply testHooks.setMosjeMP, testHooks.setOpponentMP, hand/graveyard injection
  // Record before: { ownMP, opponentMP, ownHandSize, opponentHandSize, ownGraveyardSize }
  // Click ability button: page.locator(`.mosje-card--owned[data-card-id="${spec.mosjeId}"] .mosje-ability-btn`)
  // Auto-dismiss modals (target selectors, confirm modals)
  // Record after: same fields + testHooks.getGameState() for status flags
  // Assert per expectedEffect
  // Assert log matches spec.logMatch
}
```

**Files:** `tests/ui/cards/ability-runner.js`, `tests/ui/cards/ability-registry.js`, `tests/ui/cards/mosje-abilities.spec.js`

## What a "confirmed working" card means

A card is confirmed working when its test entry is green:
- The card renders in the piecie zone after play
- Its effect produces the expected MP change (or state change)  
- The log records the action
- The card is swept to graveyard at end of turn (or persists if persistUntilEndOfTurn)

This gives the team a live dashboard: run `npm run test:ui:cards` and immediately see which cards are broken.
