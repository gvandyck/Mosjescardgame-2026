**src/multiplayer/statsStore.js** — three exports, one per file rule means each could be
its own file, BUT these three are tightly coupled (same RTDB path, same data shape) and
the project convention says "one exported function per file" applies to barrel files with
multiple unrelated exports. Keep them together as a single stats module (precedent:
walletStore.js exports three functions). File must stay under ~80 lines.

Export: `updateStats(uid, outcome)`
- outcome is 'win' or 'loss'
- RTDB path: users/{uid}/stats
- Use runTransaction so concurrent writes (e.g., both players finishing at the same
  instant on reconnect) don't corrupt counts
- Transaction receives current value (may be null); initialize to
  `{ wins: 0, losses: 0, currentStreak: 0, bestStreak: 0 }` if null
- On 'win': increment wins, increment currentStreak, update bestStreak if
  currentStreak > bestStreak
- On 'loss': increment losses, reset currentStreak to 0
- Return `{ success: true }` or `{ success: false }`

Export: `getStats(uid)`
- RTDB get on users/{uid}/stats
- Return `{ wins: 0, losses: 0, currentStreak: 0, bestStreak: 0 }` as default

Export: `getAllStats()`
- RTDB shallow get on `users` node (pass `{ shallow: true }` query param)
- Firebase RTDB shallow read: use `query(ref(db, 'users'), orderByKey())` then
  read only the top-level uid keys, NOT the full user data tree.
- Actually: RTDB does not support shallow reads via JS SDK directly. Instead,
  fetch `users` node; it will return all data. This is acceptable for leaderboard
  purposes (small dataset). Return the raw snapshot val or {} on error.
- Mark the function clearly: "Returns full users node — leaderboard fetch should
  prefer fetchLeaderboard() in leaderboardStore.js"

**src/multiplayer/leaderboardStore.js** — single export.

Export: `fetchLeaderboard()`
- isFirebaseReady guard; return [] if not ready
- Fetch the full `users` node via `get(ref(db, 'users'))`
- For each uid entry in the snapshot:
  - Skip if no stats node (unranked player)
  - Skip if no profile.displayName (anonymous-seeded account with no name)
  - Extract: displayName (from profile.displayName), wins, losses,
    currentStreak, bestStreak (from stats, default 0)
  - Compute winRate: wins / (wins + losses) — 0 if both are 0, round to 1 decimal %
- Sort descending by wins; ties broken by winRate descending
- Return array of `{ uid, displayName, wins, losses, winRate, currentStreak, bestStreak }`
  </action>

<task type="auto">
  <name>Task 3: Update database.rules.json with leaderboard read access</name>
  <files>database.rules.json</files>
  <action>
The current rules lock users/{uid} to owner-only read/write. The leaderboard needs
any authenticated user to read stats and profile for ALL users (cross-uid reads).

Restructure the users node rules to:
- Keep owner-only write on the entire users/{uid} subtree
- Add per-subnode read overrides for stats and profile

Updated rules structure:

```json
{
  "rules": {
    "users": {
      "$uid": {
        ".read": "auth != null && auth.uid === $uid",
        ".write": "auth != null && auth.uid === $uid",
        "stats": {
          ".read": "auth != null"
        },
        "profile": {
          ".read": "auth != null"
        }
      }
    },
    "rooms": {
      ".read": "auth != null",
      ".write": "auth != null",
      "$roomCode": {
        "rewards": {
          "$uid": {
            ".read": "auth != null && auth.uid === $uid",
            ".write": "auth != null && auth.uid === $uid"
          }
        }
      }
    }
  }
}
```

Note: In Firebase RTDB rules, a more-specific child rule can grant broader access than
the parent. `stats: { ".read": "auth != null" }` grants any authenticated user read
access to users/*/stats even though the parent restricts to owner. This is correct
Firebase RTDB rule cascading behaviour.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> RTDB stats write | updateStats is called client-side after match; a cheating client could call it with fabricated outcomes |
| any-auth-user -> RTDB stats/profile read | Leaderboard data is intentionally public to all signed-in users |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-01 | Tampering | updateStats / RTDB users/{uid}/stats | mitigate | RTDB write rule restricts stats writes to auth.uid === $uid — a player can only write their own stats. They cannot award themselves wins by calling updateStats for another uid. |
| T-07-02 | Tampering | claimMatchReward dedup guard | mitigate | The existing `claimed === true` flag at rooms/{roomCode}/rewards/{uid} prevents double-calling claimMatchReward (and thus double-calling updateStats) for the same match. |
| T-07-03 | Tampering | Win self-reporting (no server validation) | accept | No server-side validation of outcome. A cheating client could call updateStats('win') outside of claimMatchReward. Accepted: RTDB rules prevent writing to other players; leaderboard integrity for a friend-group game is acceptable at this fidelity. |
| T-07-04 | Information Disclosure | stats/profile readable by all auth users | accept | Intentional design — leaderboard requires cross-uid reads. Data exposed (wins, losses, displayName) is non-sensitive. |
| T-07-05 | Denial of Service | fetchLeaderboard fetches full users node | accept | Small friend-group dataset. Full node read is acceptable. If dataset grows, add pagination in a future phase. |
</threat_model>
