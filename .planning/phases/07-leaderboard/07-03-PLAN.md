Key constraint: onDisconnect hooks at users/{uid}/stats need to use `increment()`
for wins/losses fields and `set(0)` is NOT the right approach for currentStreak
(reset to 0 on disconnect-loss). The disconnect write should:
- losses: increment(1)
- currentStreak: set to 0 (not increment)
But onDisconnect().update() only supports a flat patch — not mixed set/increment
in a transaction. Solution: write a flat object with ServerValue.increment for
losses and a literal 0 for currentStreak. This is a best-effort write (not a
full transaction), which is acceptable for disconnect handling.

Opponent's win (opponentUid): similarly set wins: increment(1) and
currentStreak: increment(1). bestStreak cannot be reliably updated server-side
in onDisconnect without a transaction — accept this limitation; bestStreak
updates only via the normal claimMatchReward path.

Add new exported function `registerDisconnectLoss(roomCode, uid, opponentUid)`:

```js
/**
 * Registers RTDB onDisconnect hooks so that if this client disconnects
 * mid-match, the server automatically records a loss for them and a win
 * for their opponent.
 *
 * Call after the room is confirmed PLAYING, before the game starts.
 * Call cancelDisconnectHooks() when the game ends normally.
 *
 * No-op if uid is missing (anonymous / local mode).
 */
export async function registerDisconnectLoss(roomCode, uid, opponentUid) {
    if (!uid || !roomCode || roomCode === 'LOCAL') return;
    const ready = await isFirebaseReady();
    if (!ready) return;

    const db = getRtdb();
    const { ref, onDisconnect: getOnDisconnect, increment } =
        await import('https://www.gstatic.com/firebasejs/10.12.0/firebase-database.js');

    _disconnectHooks = [];

    try {
        // Disconnecting player gets a loss
        const myStatsRef = ref(db, `users/${uid}/stats`);
        const myHook = getOnDisconnect(myStatsRef);
        await myHook.update({
            losses: increment(1),
            currentStreak: 0,
        });
        _disconnectHooks.push(myHook);

        // Opponent gets a win (no bestStreak update — handled by claimMatchReward)
        if (opponentUid) {
            const oppStatsRef = ref(db, `users/${opponentUid}/stats`);
            const oppHook = getOnDisconnect(oppStatsRef);
            await oppHook.update({
                wins: increment(1),
                currentStreak: increment(1),
            });
            _disconnectHooks.push(oppHook);
        }
        console.log('[SYNC] Disconnect hooks registered for uid:', uid);
    } catch (err) {
        console.warn('[SYNC] Could not register disconnect hooks:', err?.code);
    }
}
```

Add `cancelDisconnectHooks()` export:

```js
/**
 * Cancels all onDisconnect hooks registered by registerDisconnectLoss.
 * Call this when a match ends normally so the hook doesn't fire on page unload.

export async function cancelDisconnectHooks() {
    for (const hook of _disconnectHooks) {
        try { await hook.cancel(); } catch (_) {}
    }
    _disconnectHooks = [];
    console.log('[SYNC] Disconnect hooks cancelled');
}
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| RTDB onDisconnect server-side write | Firebase server executes the pre-registered write when client drops — no client code runs |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-08 | Tampering | onDisconnect write to opponent's stats | mitigate | The write path is users/{opponentUid}/stats. RTDB rules require auth.uid === $uid for writes — however onDisconnect writes are executed by Firebase with the same auth context as when the hook was registered. The registering client's uid is the local player's uid, NOT the opponent's uid. This means the onDisconnect write to the opponent's stats node will be rejected by RTDB rules. Mitigation: Update database.rules.json (in a follow-up or as an addendum to this plan) to allow writing to users/{uid}/stats/wins and users/{uid}/stats/currentStreak from any authenticated user, or use a Cloud Function for server-authoritative disconnect handling. |
| T-07-09 | Tampering | Disconnect hook write to own stats | accept | Player can only write a loss to their own stats via onDisconnect. Writing a loss to yourself is not an exploitable cheat. |
| T-07-10 | Elevation of Privilege | Opponent win write rejected by rules | accept short-term | If T-07-08 is not resolved, the opponent simply does not receive the win credit from onDisconnect. Their normal claimMatchReward runs if they stay in the game and the room status updates to FINISHED. This is acceptable for the current phase — full server-authoritative disconnect handling (Cloud Functions) is a future enhancement. |
</threat_model>
