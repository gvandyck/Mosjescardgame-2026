# Phase 31 — Plan 01: MP 0–100 Cap Invariant

## Goal
Enforce the canonical rule (phase0-rulings.md): **a Mosje's MP is always 0–100.**
It must never exceed 100. **Only Quests permanently level up** a Mosje (reaching
100 via a Quest reward → Level +1, MP resets to 0). Piecies, Places, abilities,
snelles, and the turn trickle **cap at 100** and never permanently level.

The lower bound (below 0 → defeat) is already done (Phase 30). This phase is the
**upper bound** + the quest-only-leveling distinction.

## Current behavior (the violation)
- `checkLevelUp` (mpManager.js) converts MP ≥ 100 into Levels (mp -= 100, level += 1).
  It is only reached via `gainMP` (mpManager.js:47 and :268).
- **Non-quest gains do NOT cap.** ~50 scattered `slot.mp += X` sites across
  `piecieEffects.js`, `mosjeAbilities.js`, `placeEffects.js`, `snelleEffects.js`,
  plus `applyMPGain` (piecieEffects.js:43) and a couple in `turnManager.js`, add
  MP with no clamp — so a Mosje can sit at 105 (confirmed: card-chains.spec.js
  "piecie MP gain caps at 100" expected-failure, Lv0/80 + Kannetje +25 → 105).
- Some **abilities call `gainMP`** (which levels via checkLevelUp). Per the rule
  only Quests should permanently level, so any non-quest `gainMP` caller that can
  reach 100 would wrongly level up.

## Architecture decision: central clamp sweep (mirror Phase 30)
Rather than edit ~50 gain sites (error-prone, easy to miss new cards), enforce the
ceiling in ONE place — exactly how `applyPendingDefeats` enforces the floor:

1. Add `clampMosjeMp(gameState)` in `src/engine/victoryChecker.js`: for every
   non-defeated active slot, `slot.mp = Math.min(100, slot.mp)`. (Floor already
   handled by loseMP/defeat; this only caps the ceiling.)
2. Call it at the **top of `checkVictory`**, right after `applyPendingDefeats`
   (checkVictory already runs after every action — one central hook). By the time
   anything renders or the next action runs, no Mosje is above 100.
3. The Quest level path is untouched: `gainMP → checkLevelUp` converts ≥100 into a
   Level *during* the quest resolution, so the Mosje is already < 100 before the
   clamp sees it. Non-quest gains that overshoot to 105 get clamped to 100.

> Why central + sweep: same proven pattern as defeat-at-0. New MP-gain cards are
> automatically covered without touching their effect code.

### The quest-vs-non-quest leveling nuance (Task 2)
The sweep caps the ceiling, but we must also ensure **only Quests level**:
- Audit the `gainMP` callers (mosjeAbilities.js, questLogic.js, turnManager.js).
- Quest rewards (questLogic.js `resolveQuest`) SHOULD keep using the leveling
  `gainMP`/`checkLevelUp`.
- Any **non-quest** caller of `gainMP` that could reach 100 (e.g. an ability) must
  NOT permanently level — route it through a capped gain instead (or pass a flag).
- If an ability is *meant* to temporarily level (per card text), that's the separate
  "temporary level" mechanic — out of scope here; note it, don't build it unless a
  card needs it.

## Tasks

### Task 1 — Add the `clampMosjeMp` sweep
- New exported `clampMosjeMp(gameState)` in `victoryChecker.js`: clone, iterate all
  players' `activeSlots`, set `mp = Math.min(100, mp)` for non-null/non-defeated.
- Call at top of `checkVictory` after `applyPendingDefeats`, before win checks
  (so a Mosje clamped to 100 is what KNOCKOUT/level checks see).
- Guard: idempotent, no-op when all ≤ 100.
**Verify:** unit test — a slot at 105 → 100 after checkVictory; a slot at 100 stays 100; ≤100 untouched.

### Task 2 — Audit gainMP callers; separate "level" from "cap"
- `grep -rn "gainMP(" src/` — classify each caller as Quest (keep leveling) or
  non-quest (must cap, not level).
- For non-quest callers that can reach 100: either switch to a capped path or add a
  `{ allowLevelUp = false }` option to `gainMP` and default non-quest callers to it.
- Document findings in a short note appended to this plan (or CONTEXT.md).
**Verify:** no non-quest effect can push a Mosje to Level +1; quest rewards still level.

then tests + sim.)

## Success criteria
1. No Mosje ever holds MP > 100 (or < 0) after any action — enforced centrally.
2. Only Quests permanently level up; piecies/places/abilities/snelles cap at 100.
3. Quest rewards still level up correctly (≥100 → Level+1, MP resets, overflow carries).
4. card-chains "piecie MP gain caps at 100" passes (test.fail removed); new mp-cap unit tests pass.
5. `npm test` + `npm run test:cards` green; Ronald Kip stacking test green.
6. Simulation crash-free, timeout < 25%; bot-vs-bot shows no MP > 100.
7. `node --check` clean.

## Risk notes
- **Quest leveling regression**: capping too aggressively could stop quests from
  leveling. Mitigation: the sweep runs AFTER checkLevelUp (which already reset mp<100),
  so it never interferes with quest level-ups. Task 2 keeps the quest gainMP path intact.
- **Hidden non-quest gainMP leveler**: an ability using gainMP could currently level;
  Task 2 audit catches these. If found, switch to capped gain.
- **Temporary-level mechanic**: not built; only add if a specific card requires it
  (track separately).
- Balance: capping reduces runaway MP; re-baseline bot-vs-bot (Task 5).
